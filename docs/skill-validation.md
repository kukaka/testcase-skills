# 两份测试 Skill 的设计与验证记录

## 2026-10-29：执行方法层

### 缺口盘点

执行侧已有闸门、断言与证据纪律、四类状态判定、首次失败保留，基础扎实。缺口集中在"判定之后"：根因只有禁令（"不要为了给出根因而推测"）没有方法；最小复现、复现率、严重程度只在缺陷记录模板里出现字段名；回归范围只有一句"检查直接受影响的回归范围"；探索式测试、夹具管理、幂等与并发、证据分级、变更影响分析完全没有。

### 决策

先做第一批四项：**失败诊断与最小复现**、**证据分级**、**变更影响与回归范围**、**缺陷报告与严重程度、优先级**。第二批（探索式测试、测试数据与夹具、并发与幂等）暂不纳入。

执行侧的"选法"判据用**执行阶段 × 现场情况**，与设计侧的"按业务结构"对应。

### 行为试用：执行侧

### 验证边界

- 只有一组合成缺陷、每组一次运行，不足以做统计推断。
- 对照组本身已经相当强——改版前的执行 skill 在断言、证据、判定、首次失败保留上并不薄弱，因此方法层在执行侧的边际收益明显小于设计侧。可量化的增量主要是：结论标注证据层级、严重程度与优先级分离、复现率、已排除项、回归范围的分档与依据密度。
- 两组都出现了"读源码定位根因"的行为。方法层据此补了一条规则：读代码定位是合法手段，但它给出的是对实现的推断而非对现象的观察，写进缺陷记录时必须标为推断，断言只写观察到的行为，"代码看起来没改"不能计入 PASS 或回归范围的排除依据。
- 未覆盖真实浏览器、真实账号、真实后端与基线切换后的恢复。

## 2026-10-29：澄清闸门改版

本节记录闸门改版的设计与行为验证。下方 2026-10-28 的记录描述的是**闸门改版前**的版本，两者语义不同，不可混用。

### 改版动机

初版采用的是"边问边做"：澄清问题可以挂着，先把不依赖答案的部分做完，再交付标注为待澄清的产物。用户明确要求相反的行为——**不明确就整体停下来提问，拿到明确答案再继续**。初版的表述（"等待答复期间继续独立部分""允许交付标注候选预期的草稿""执行不依赖它的用例"）与该要求直接冲突，因此不是措辞调整，而是语义改版。

### 语义变化

| 场景 | 改版前 | 改版后 |
|---|---|---|
| 设计侧遇到未知规则 | 提问，同时继续设计其余用例，交付带 `NEEDS_CLARIFICATION` 的草稿 | 停止设计，一次问清全部闸门问题，拿到答复前不产出用例文件 |
| 执行侧遇到条件缺失 | 记录阻塞并提问，继续执行不依赖它的用例 | 记录阻塞、提问、停止本轮，不执行新用例 |
| 部分答复 | 关闭已答部分，其余标为待澄清继续推进 | 拆出未解子问题，继续停机 |
| 交付物 | 可含未决预期的用例 | 交付时不得存在 `NEEDS_CLARIFICATION` 用例或未关闭的 `Q-xxx` |
| "按你理解先出一版" | 可写候选方案和用例骨架 | 视为明确授权，可继续，但须记录授权原话、所选规则与残余风险 |
| 沉默与超时 | 未明确禁止当作答案 | 明确不是答复，不得当作答案 |

### 行为试用：写作侧，第一轮

独立 agent 只拿到 skill 目录与合成需求（`docs/validation/fixtures/writing-prd.md`），需求中故意埋了三处未明确项：有效期 3 天与原型 7 天冲突、有效期起算锚点未定义、接受后成员角色未定义；另有两项由需求直接排除（批量邀请、邮件发送本身）。

结果：

### 行为试用：执行侧

目标为 `docs/validation/fixtures/target.py`（本地命令模拟的草稿系统），用例见 `fixtures/execution-cases.md`，包含一条需要管理员会话的导出用例和两条普通成员用例。

### 验证边界

- 三轮试用都是合成场景，只覆盖"闸门是否触发、是否停止、答复能否落地"这一条行为链，没有覆盖真实浏览器、真实账号、真实后端与基线切换后的恢复。
- 写作侧第一轮一次提出 8 个问题。问题数量偏多但都在一次内问清，符合"不反复往返"的要求；是否过细（部分问题可视为同一决定的不同侧面）没有量化标准，属于待观察项。
- 没有做无 skill 的对照实验，不能据此量化相对模型默认能力的提升。
- 执行侧第一轮的用例乱序说明：skill 只约束"命中闸门即停"，不约束执行顺序本身；顺序由"按风险和显式依赖排序"决定，实际项目若使用固定回归顺序，闸门会出现在轮次中段而非末尾。

## 2026-10-28：初版设计与验证

日期：2026-10-28。对象：`skills/test-case-writing/` 与 `skills/test-case-execution/`。

### 本轮设计选择

- 编写阶段交付规则依据、问题与用例关联、设计就绪状态、步骤断言、覆盖缺口和执行条件；执行阶段按同一语义接收，也支持其他来源的用例格式。
- 澄清是实际交互：查已有材料，提出影响判定的问题，继续独立部分；答复后同步修订规则、用例和覆盖表。业务规则不明与执行实例未准备分别处理。
- 通过须由全部断言的实际观察支持。保留首次失败、诊断重试、未验证断言和修复后复测的区别；不以工具成功、提示成功或零条测试运行证明业务通过。
- 恢复前重查前置状态；构建或需求基线改变后不合并旧 PASS。主文件负责判断与推进，模板和具体案例位于各自 references 中。
