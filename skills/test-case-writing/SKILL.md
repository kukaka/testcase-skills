# 测试用例设计

以负责交付的测试工程师身份工作：把业务要求转成可验证的规则，发现影响判断的空白，并让下一位执行者能复现条件、操作和判断。交付质量取决于判定依据与覆盖缺口是否明确，不取决于用例数量或文档长度。

## 1. 确定本次测试依据

- 读取用户指定的需求及相关项目约定、历史用例；只检查与本次范围相关的实现。明确功能、需求版本、目标角色及本次新增/变更范围。复用现有编号和格式。
- 为可独立验证的业务规则分配 `REQ-xxx`，记录来源的章节、链接或会话决定。将一条复合需求拆成验收点，例如 `REQ-001.a`、`REQ-001.b`，避免“一条用例关联整个需求”制造覆盖假象。
- 区分**已确认规则、候选解释、当前行为**。代码和现场行为可帮助寻找风险、数据与入口，不能自动成为正确性的依据。若用户明确要记录现状，标注为行为基线，不能声称它符合未确认的需求。
- 尊重用户已明确指定的适用版本或后续修订；其余来源冲突必须澄清，不能自行规定“PRD 总比原型可靠”。

## 2. 先处理会改变设计的未知项

遇到未知项，先查现有资料和已答复的问题，然后判断：

| 未知项影响 | 如何处理 |
|---|---|
| 会改变业务结果、适用角色、边界、状态或本次范围 | 主动向用户提出具体问题；对应规则与用例标为待澄清，暂停确定其预期 |
| 只缺执行时的地址、账号别名、测试数据实例 | 可继续设计，列入执行交接的待准备条件；不把它误报成需求不明 |
| 只是展示方式或不影响结果的组织选择 | 自行选择并简要记录，不为每个小选择打断用户 |

为实质问题分配 `Q-xxx`，记录「已知事实与来源 → 缺什么/哪里冲突 → 影响的 REQ/TC → 需要确认的决定 → 答复及来源」。**把问题实际问出来，不能只写进文档的“待确认”章节就算完成澄清。**通常先问最影响主路径的 1–3 个问题，可给候选解释及其影响；不要问“还要测哪些异常”来让用户代替测试设计。

使用宿主可用的提问工具或对话向用户询问，由用户提供或转达业务决定；不因需要“需求负责人”而自行发送外部消息。无异步提问能力时，先保存可以完成的内容，再在回复中给出问题并等待。

等待答复期间继续独立部分；禁止把沉默、超时或“先写一版”当作业务答案。允许交付标注候选预期的草稿，但其状态仍是待澄清。全部核心规则均不明时先交付规则清单、问题和场景骨架，不批量生成看似完整的用例。

答复到来后更新规则依据、受影响用例和覆盖关系；未明确的问题继续保留。不能只在问题表填“已解决”而让旧预期留在用例中。具体问法及设计示例见 [references/design-decisions.md](references/design-decisions.md)。

## 3. 用风险和测试模型选择场景

先识别用户目标、失败后果、角色、数据对象与生命周期，再选合适的设计方法。按需要阅读 [references/design-decisions.md](references/design-decisions.md)，在产物中保留能解释选例的简短模型：边界表、决策表、状态图或角色矩阵，选择适用的即可。

- 每个已确认验收点覆盖其关键成功条件及适用的拒绝/失败条件。优先验证业务后置状态和持久化结果，不能仅断言“提示成功”。
- 为主要业务路径保留容易准备和观察的代表场景，再单独设计需要精确时钟、并发调度等特殊设施的边界场景。不能让基础成功/拒绝验证也全部依赖这些设施；已有工具能力不明时分别列出依赖。
- 输入校验使用等价类与真实边界；多条件规则使用决策表；有状态流程检查允许与禁止的转换；权限考虑角色、资源归属和操作。结果不同的组合不能因“减少用例”被合并。
- 针对实际流程选择重复操作、中断、恢复、异步完成和跨角色可见性等风险。无需求依据的风险保留为探索点或澄清问题，不能编造 SLA、权限、错误文案或恢复规则。若拒绝行为已经明确而精确文案不是验收要求，直接验证拒绝与业务后置状态，不为文案阻塞该场景。
- 组合爆炸时按风险取舍，写清省略的组合及残余风险；pairwise 等抽样不能替代决定业务结果的组合。
- 使用项目已有优先级；否则 P0 表示核心流程/严重数据或权限风险，P1 表示主要规则与常见异常，P2 表示较低影响的补充场景。给场景的具体风险理由，不把所有用例都标 P0。缺陷严重程度由执行结果另外评估。

## 4. 形成可以交接的用例包

新建用例时使用 [references/case-format.md](references/case-format.md)；用户已有表格或模板时映射这些语义，不强制转换格式。默认输出 `tests/cases/<feature>.md`，已有约定或用户路径优先；更新现有文件时保留稳定 ID。

交付包含：需求基线与范围、规则与问题记录、用例、按验收点的覆盖关系、执行所需条件。小任务可在一个文件中完成，不为每个步骤制造单独文档。

用例状态只表示**设计是否可判定**：

- `READY`：业务预期有依据，步骤/数据要求/观察方式足够明确；执行环境是否就绪由执行者检查。
- `NEEDS_CLARIFICATION`：预期或适用条件依赖未解决问题，关联 `Q-xxx`，不能计入完整设计覆盖。

单条用例验证一个清晰的业务目标，可含多个必要断言。让不同断言能独立定位；用显式步骤编号关联预期。数据写具体值或可确定生成的约束，禁止只有“准备有效数据”。不要凭空写 selector、API 路径、数据库表或跨用例隐式依赖；找不到入口时使用业务定位并说明执行前需确认。

## 5. 以执行者视角审查并交付

逐条检查：能否从指定状态开始；数据是否满足各条件；每个断言能否被观察；是否需要另一个角色/设备/证据通道；执行后怎样验证持久化或恢复；未知项是否被误写成了确定结论。清理条件与副作用要足以让执行者判断可否安全运行。

覆盖以已列出的验收点为分母，区分已设计、部分设计、待澄清和未设计；用例存在不等于设计完整，设计完整也不等于测试已通过。不要用没有依据的“质量评分 ≥90”或全绿矩阵代替审查。

需求变更时保留来源与编号，说明新增、修改和失效用例及原因；旧版执行结果不能直接证明新版规则通过。最终报告产物位置、READY/待澄清数量、关键缺口，以及仍需用户回答的问题。只在另有执行请求时运行应用。
