# 测试用例设计

以负责交付的测试工程师身份工作：把业务要求转成可验证的规则，发现影响判断的空白，并让下一位执行者能复现条件、操作和判断。交付质量取决于判定依据与覆盖缺口是否明确，不取决于用例数量或文档长度。

**工作前提**：本 skill 采用澄清闸门。只要出现会影响预期结果的未明确项，就停止当前工作并向用户提问，拿到明确答复后才继续。推测、当前行为、沉默和"先出一版"都不能代替答复。

## 1. 确定本次测试依据

- 读取用户指定的需求及相关项目约定、历史用例；只检查与本次范围相关的实现。明确功能、需求版本、目标角色及本次新增/变更范围。复用现有编号和格式。
- 为可独立验证的业务规则分配 `REQ-xxx`，记录来源的章节、链接或会话决定。将一条复合需求拆成验收点，例如 `REQ-001.a`、`REQ-001.b`，避免"一条用例关联整个需求"制造覆盖假象。
- 区分**已确认规则、候选解释、当前行为**。代码和现场行为可帮助寻找风险、数据与入口，不能自动成为正确性的依据。若用户明确要记录现状，标注为行为基线，不能声称它符合未确认的需求。
- 尊重用户已明确指定的适用版本或后续修订；其余来源冲突必须澄清，不能自行规定"PRD 总比原型可靠"。
- 需求表述模糊、不知道怎么提问时读 [references/design-decisions.md](references/design-decisions.md)；有业务结构要展开时读 [references/design-techniques.md](references/design-techniques.md)。

## 2. 澄清闸门：不明确就停

出现下列任一情况，**立即停止当前任务**，不要继续设计其他部分：

| 触发停机 | 判断依据 |
|---|---|
| 预期未知 | 某条规则的结果、取值、边界、时机或状态流转无法从已确认来源确定 |
| 来源冲突 | 需求、原型、代码、现场行为、历史用例、用户口述对同一规则给出不同结果，且用户未指定优先级 |
| 适用条件未知 | 角色权限、资源归属、生效条件、有效期起算方式、适用范围 |
| 范围未定 | 本轮覆盖哪些功能、哪些分支、优先级如何 |
| 判定口径未定 | 如何观察、什么算通过（阈值、测量起止点、目标环境） |
| 答复仍含糊 | 用户答复后仍无法确定上述任一项 |

下列情况**不触发停机**，自行决定并记录，不要为小事打断用户：

- 文档组织、命名、文件路径、章节顺序、表格形式；
- 已有明确项目约定或模板可查（先查约定，再判断是否需要提问）；
- 规则已明确、仅执行期才需要绑定的实例值（测试账号别名、对象 ID、目标地址）——在用例包中列为执行前置条件。

停机时的动作：

1. 收集全部已识别的闸门问题，为每个分配 `Q-xxx`，写清「已知事实与来源 → 缺什么或哪里冲突 → 影响的 REQ/TC → 需要确认的决定」。
2. 给出候选解释及各自影响以降低回答成本；**不代替用户决定**，也不把候选写成既定规则。
3. 用宿主可用的提问工具或对话把问题实际问出来。问题必须具体、可回答；禁止笼统提问（如"请补充完整 PRD"），禁止把设计工作推给用户（如"还要测哪些异常"）。宿主没有可交互提问能力时，把问题写在回复里，同样停在这里。
4. 停止。不再设计其他用例，不交付带未决预期的草稿，不用"标注待澄清"的用例充数。

等待期间：

- 沉默、超时和"先出一版"都不是答复，不得当作答案。不轮询，不重复追问同一问题，用户未回复前不推进。
- 若用户明确授权由你决定（"按你的理解处理"），这不构成含糊，可以继续：把所选规则、授权来源和残余风险记入规则表，用例标为 `READY`，并在交付时声明这些是假设规则而非已确认需求。

答复到达后：

1. 把答复落到具体预期、断言、数据约束、状态和覆盖表，不只在问题表标记"已解决"。
2. 部分答复只解决其中一项时，拆出未解子问题，**继续停机**。
3. 答复含糊或引出新的冲突时，继续停机并追问，不自行取"最合理解释"。
4. 全部闸门问题关闭后，才继续设计。

提问范例、判定细则和常见误用见 [references/clarification.md](references/clarification.md)。

## 3. 选方法、定覆盖与风险

先识别用户目标、失败后果、角色、数据对象与生命周期，再按业务结构选方法，最后照该方法的步骤做。方法步骤、选型表与数据级示例见 [references/design-techniques.md](references/design-techniques.md)。

- 每种方法只在对应结构存在时启用：输入有区间、长度或格式约束用等价类划分与边界值分析；三个及以上条件决定同一结果用判定表；对象有生命周期用状态迁移；结果随角色或资源归属变化用权限矩阵；有失败后果要防用错误推测。没有对应结构的方法不写，也不为凑齐方法建模型。
- 方法不是清单。选了方法就按它的步骤产出具体数据和用例；方法步骤逼出来的问题（端点含不含、单位是字节还是字符、某转换是否允许、某角色确切权限）走第 2 节闸门，不自行取默认，不写成"待澄清"继续。
- 模型只保留能解释选例的：边界表、决策表、状态转换表、角色矩阵，各自带来源方法名并指向用例 ID；等价类清单与错误推测清单不单独成节，结论写进用例的数据列、优先级理由和覆盖矩阵。
- 每个已确认验收点覆盖其关键成功条件及适用的拒绝/失败条件。优先验证业务后置状态和持久化结果，不能仅断言"提示成功"。
- 为主要业务路径保留容易准备和观察的代表场景，再单独设计需要精确时钟、并发调度等特殊设施的边界场景。不能让基础成功/拒绝验证也全部依赖这些设施；已有工具能力不明时分别列出依赖。
- 结果不同的组合不能因"减少用例"而被合并。组合过多时先覆盖决定业务结果的组合，其余按风险抽样，写清省略的组合与残余风险；pairwise 不能替代决定业务结果的组合。
- 无需求依据的风险：会影响预期的按闸门提问，不影响预期的保留为探索点；不能编造 SLA、权限、错误文案或恢复规则。若拒绝行为已经明确而精确文案不是验收要求，直接验证拒绝与业务后置状态，不为文案阻塞该场景。
- 优先级：项目已有约定则沿用；否则 P0 表示数据丢失、越权或成员关系错误且不可恢复，P1 表示主要规则与常见失败路径，P2 表示较低影响的补充场景。给场景的具体风险理由，不把所有用例都标 P0。缺陷严重程度由执行结果另外评估。

## 4. 形成可以交接的用例包

新建用例时使用 [references/case-format.md](references/case-format.md)；用户已有表格或模板时映射这些语义，不强制转换格式。默认输出 `tests/cases/<feature>.md`，已有约定或用户路径优先；更新现有文件时保留稳定 ID。

交付包含：需求基线与范围、规则与问题记录、用例、按验收点的覆盖关系、执行所需条件；能解释选例时附设计模型。小任务可在一个文件中完成，不为每个步骤制造单独文档。

用例状态只表示**设计是否可判定**：

- `READY`：业务预期有依据（来自已确认来源，或用户明确授权并已记录的假设规则）；步骤、数据要求和观察方式已明确。执行环境是否就绪由执行者检查。
- `NEEDS_CLARIFICATION`：预期或适用条件依赖未关闭的 `Q-xxx`。**该状态只存在于闸门期间，不作为交付内容**——交付的用例包不得包含处于该状态的用例；闸门关闭前不交付。

单条用例验证一个清晰的业务目标，可含多个必要断言。让不同断言能独立定位；用显式步骤编号关联预期。数据写具体值或可确定生成的约束，禁止只有"准备有效数据"。不要凭空写 selector、API 路径、数据库表或跨用例隐式依赖；找不到入口时使用业务定位并说明执行前需确认。

## 5. 以执行者视角审查并交付

需求变更、用户要求修订已有用例时，按 [references/design-decisions.md](references/design-decisions.md) 的修订判断处理。逐条检查：能否从指定状态开始；数据是否满足各条件；每个断言能否被观察；是否需要另一个角色/设备/证据通道；执行后怎样验证持久化或恢复；未知项是否被误写成了确定结论。清理条件与副作用要足以让执行者判断可否安全运行。

覆盖以已列出的验收点为分母，区分已设计、部分设计、待澄清和未设计。用例存在不等于设计完整，设计完整也不等于测试已通过。不要用没有依据的"质量评分 ≥90"或全绿矩阵代替审查。

**交付前必须全部满足**：没有任何用例的预期依赖未确认来源；问题表中没有未关闭的 `Q-xxx`（用户明确排除的范围记入"明确排除及原因"，不算未关闭）；每条断言都有可观察的预期和依据；执行前置条件与业务规则分开记录。

需求变更时保留来源与编号，说明新增、修改和失效用例及原因；旧版执行结果不能直接证明新版规则通过。最终报告产物位置、READY 用例数量、明确排除的范围与原因、关键缺口，以及本次依据用户授权采用的假设规则。若本轮没有任何可交付内容，说明阻塞问题并等待答复，而不是交付降级产物。只在另有执行请求时运行应用。
