# 设计与澄清的具体判断

在不知道如何提问，或需求变更后需要修订用例时使用。选测试方法见 [design-techniques.md](design-techniques.md)。

## 把模糊要求变成可回答的问题

需求："支持上传 Excel，大文件也要快，失败可以重试。"

不要先生成"支持 10 MB / 3 秒以内 / 自动重试三次"等虚构规则，也不要询问笼统的"请补充完整 PRD"。先查看已有上传约定，仍缺失时问：

> Q-001：当前需求没有定义支持的扩展名、大小上限及超限后的结果，这会影响格式与边界用例。请确认是否支持 xls、xlsx，以及单文件限制和拒绝方式。
>
> Q-002："失败可重试"是重新上传整个文件，还是只重试失败行？这决定如何检查重复数据和部分成功后的状态。

性能不在本轮验收范围时，不因缺少阈值而停机；一旦性能属于本轮验收，缺失阈值即触发闸门——问清测量起终点、数据规模、环境与阈值，拿到答复前不继续设计。候选解释用来减少回答成本，不代表推荐答案已获批准。

答复"只支持 xlsx，大小限制稍后定"只解决格式问题。关闭已解部分，把大小拆成未解子问题，**整个设计继续停在闸门上**——不因为格式问题有答案就先把格式用例交付出去。问题表不能只记一个笼统的"已回复"。

## 何时把模型写下来

模型指边界表、决策表、状态转换表、角色矩阵——由具体设计方法产出的表格，用来解释选例，不是需求本身。

只在能解释选例时保留：每一行都指向具体用例，且能回答"为什么只测了这些组合"。判断标准与四种形态的写法见 [design-techniques.md](design-techniques.md) 的"模型产物：留与不留"。

等价类清单和错误推测清单通常不单独成节，把结论写进用例的数据列、优先级理由列和覆盖矩阵即可。为凑齐方法而建模型不算解释选例。

## 修订用例时的判断

- 规则改变：更新预期与来源，标出受影响断言及待复测范围，保留 ID；不能把旧规则下的 PASS 带到新规则。
- 仅改文案或路径且不影响判定：保持业务目标与 ID，修正操作定位；有文案精确匹配要求时另行处理。
- 决定减少范围：记录移出项、原因和残余风险，不把删除后的空白标为已覆盖。
- 用户说"按你理解先出一版"：这句话本身是**授权**，不是含糊。可以继续设计，但被委托的规则要记录授权原话、所选规则和残余风险，不假装它来自原 PRD；未被委托的其它未知规则仍然停机。
- 答复本身含糊：例如用户说"差不多按常规来吧"。这不是授权，继续停机并追问具体口径；只有用户明确表示"你定"才算授权。
