# 澄清闸门：判定与提问

在不确定某项是否需要提问、怎么问、或答复到手后如何落地时使用。

## 什么是"已确认来源"

只有以下来源能让预期成为 `READY`：

- 用户在本次会话中的明确答复；
- 需求文档中明确的验收点，且用户未提出相反约束；
- 用户明确授权由你决定的规则——须记录授权原话和所选规则。

以下**不是**已确认来源：代码当前行为、原型截图、线上现状、你自己的常见做法、上一轮会话的结论。它们是线索和风险来源，只能用来提问，不能用来定预期。

## 什么必须停，什么不用停

| 情况 | 处理 |
|---|---|
| 需求说"大文件也要快"，没有阈值 | 停。若性能属于本轮验收，问清测量起终点、数据规模、环境与阈值 |
| 需求说"支持 Excel"，未说格式 | 停。问支持哪些扩展名、单文件上限、超限后的结果 |
| 拒绝时的错误文案没写，但拒绝行为已明确 | 不停。直接验证拒绝行为与业务后置状态，文案不作为断言 |
| 用例文档放在 `tests/cases/` 还是 `test/cases/` | 不停。查项目约定，没有就用默认值并记录 |
| 测试账号具体是哪个还没分配 | 不停。角色和权限已确定即可设计，实例值列为执行前置条件 |
| 同一规则 PRD 写 3 天、原型写 7 天 | 停。问适用版本，不自行决定优先级 |
| 用户答复"大小限制稍后定" | 部分答复。只关闭格式问题，大小边界继续停机 |
| 用户答复"就按 10MB 吧" | 明确授权。继续设计，标记为假设规则并在交付时声明 |

## 提问的写法

每个问题四段：已知事实与来源 → 缺什么或哪里冲突 → 影响的 REQ/TC → 需要确认的决定。可以附候选解释降低回答成本，但候选不是答案。

反例（不合格）：

- "请补充完整的需求文档。"——不可回答，用户不知道该补什么。
- "还需要测哪些异常场景？"——把设计工作推给用户。
- "失败的时候提示什么？"——问题太小、缺上下文。
- "要不要测一下并发？"——先给答案找理由。

正例：

> Q-002：PRD 写"上传失败可以重试"，但没说重试粒度，也没有说明部分行成功后的状态。这决定重复数据是否产生、以及要检查草稿的哪部分状态。请确认：是重传整个文件，还是只重试失败行？
>
> 候选解释：(a) 整体重传，失败行不落库；(b) 只重试失败行，已成功行保留。两者要检查的字段不同。

## 常见误用

| 误用 | 为什么不行 | 正确做法 |
|---|---|---|
| 用当前代码行为填补未知预期 | 把现状当需求，掩盖真实缺陷 | 提问；用户明确要记录现状时标为行为基线 |
| 缩小问题范围以便回答 | 静默改变了本轮范围 | 问；用户缩小范围时记入"明确排除及原因" |
| 把候选解释写成既定规则 | 你替用户做了业务决定 | 候选只写在问题里 |
| 沉默或超时当作答复 | 沉默不是业务答案 | 停在闸门上等待 |
| 先写一版再问 | 交付带未决预期的产物 | 先问；用户明确授权除外 |
| 一次只问一个问题，多问几轮 | 拖延且增加往返 | 收集全部闸门问题一次问清 |
| 答复后只更新问题表 | 旧预期仍留在用例里 | 同步改预期、断言、数据约束、覆盖表 |
| 答复含糊时自行取"最合理解释" | 你的解释没有来源 | 二次澄清 |

## 答复落地

答复到手后按顺序处理：

1. 逐条对照答复，确认它关闭了哪个 `Q-xxx`、哪几个 `REQ`。
2. 更新规则表的来源列（写"用户答复"或答复时间点），不要只改预期不改依据。
3. 更新受影响用例的预期、断言、数据约束、状态字段；保留用例 ID。
4. 更新覆盖矩阵的已设计/部分设计状态。
5. 检查答复是否引出新问题（例如确定了上限但没定超限行为），有则继续停机。

## 授权路径

用户明确说"按你的理解处理""你定就行"时：

- 这构成授权，不是含糊，可以继续；
- 在规则表记录授权原话、所选规则和残余风险；
- 用例标为 `READY`，但预期依据写"用户授权的假设规则"，不写成需求原文；
- 交付时单列这些假设，让用户事后修正。

授权只覆盖被委托的那一项。未被委托的其他未知项仍然停机。
