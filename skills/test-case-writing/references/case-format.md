# 用例交接格式

这是默认 Markdown 格式及字段语义。可映射到用户已有表格；不要丢失规则依据、就绪状态、问题关联和步骤断言。占位符是模板示意，交付时替换为实际内容；未知业务值须关联澄清问题。

## 用例包结构

```markdown
# <功能>测试用例

## 基线与范围
- 需求来源/版本/定位：
- 本次目标与包含范围：
- 明确排除及原因：
- 执行条件：环境类型、角色、设备/工具能力、数据准备与副作用约束

## 规则与待澄清问题
| 规则 ID | 验收点 | 来源 | 已确认/待澄清 | 问题 ID |
|---|---|---|---|---|

| 问题 ID | 已知事实/冲突 | 需要决定什么 | 影响 REQ/TC | 状态 | 答复、来源及影响更新 |
|---|---|---|---|---|---|

## 用例
### TC-<功能>-001：<业务目标>
- 规则：REQ-xxx.a；预期依据：<来源定位或确认答复>
- 设计状态：READY / NEEDS_CLARIFICATION；问题：Q-xxx 或无
- 优先级与理由：
- 角色/入口：<身份要求及业务入口，不放凭据>
- 前置状态：<对象状态、依赖和验证方法>
- 数据：<具体值、生成约束、资源归属；环境实例可由执行者绑定>

| 步骤 | 动作与数据 | 断言 ID | 可观察预期及观察方式 |
|---|---|---|---|
| 1 | ... | A1 | ... |

- 等待条件：<如任务进入完成态；时限仅引用已约定值，否则注明>
- 清理/后置状态：<本次数据如何处理，有无不可逆副作用>

## 设计覆盖
| 规则/验收点 | READY 用例 | 待澄清用例/问题 | 已设计/部分设计/待澄清/未设计 | 缺口与风险 |
|---|---|---|---|---|
```

步骤中的纯准备动作可以没有断言；所有用来判断结果的断言使用用例内唯一 ID。一次用例内的多个必要断言各自记录，不以一句“正常显示”概括。无状态变更时清理写“不需要”，不强加环境操作。

`READY` 不承诺测试环境已上线或账号已创建。例如角色必须是管理员已确定，具体测试账号尚未分配，设计仍可 READY，交接中注明待准备；是否允许普通成员操作未定，则相关权限用例必须 NEEDS_CLARIFICATION。

## 示例：已确认规则与执行实例分开

已确认 `REQ-D.a`：普通成员可将**自己的草稿**改名为 1–20 个 ASCII 字母，保存后重新打开仍显示新名称，且改名不改变归属与草稿状态。拒绝名称的文案及空值处理另有待澄清问题。

### TC-D-001：成员保存自己草稿的新名称

- 规则：REQ-D.a；依据：上述确认规则。
- 设计状态：READY；优先级：P1，验证编辑后的持久性。
- 角色/入口：普通成员，自己的草稿详情页。
- 前置状态：可用的成员会话；一条归属于该成员、名称为 `OldDraft` 的草稿。执行前记录实际对象 ID，并确认状态为草稿。
- 数据：新名称 `NewDraft`；通过项目已有方式创建一次性草稿，具体账号和对象 ID 在执行记录中绑定。

| 步骤 | 动作 | 断言 ID | 预期与观察方式 |
|---|---|---|---|
| 1 | 打开已记录 ID 的草稿，将名称改为 `NewDraft` 并保存 | A1 | 当前草稿名称显示为 `NewDraft` |
| 2 | 离开详情后重新打开相同 ID 的草稿 | A2 | 名称仍为 `NewDraft`，归属和草稿状态未改变 |

- 等待：页面保存动作完成且名称可读取；未给定性能时限，不据此判定性能达标。
- 清理：测试环境允许删除时只删除本次创建的草稿；否则记录残留 ID。

不要根据这个成功用例推断“名称长度 0 必须弹出某句错误”。将未知拒绝规则关联问题，已确认的成功场景仍可设计并交接。
