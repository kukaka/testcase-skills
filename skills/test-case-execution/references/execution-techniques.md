# 执行技术：选型与操作

本文件回答三个问题：这次执行要用哪种技术？怎么做？结论怎么落到可信的证据和可用的缺陷单上。

**本文件不改变 SKILL.md 第 2 节的澄清闸门语义。** 方法不新增停机条件。但方法本身需要额外授权时（读服务端日志、连数据库、改配置、造数据、访问监控），走第 2 节闸门，不为了定位问题自行扩权。

## 选型程序

1. **定位现场**：确定这次在做什么（准备、执行、观察、判定、诊断、报告、复测），以及现场状态（PASS、FAIL、BLOCKED、结果不稳定、修复后复测）。
2. **选技术**：按选型表映射到方法。表里没有的现场，先看各方法的"何时不用"。
3. **照步骤做**：按该方法"怎么做"的编号步骤做，产出实际证据。
4. **收口**：确认结论落到 PASS、FAIL、BLOCKED 或 NOT_RUN，且每个结论有证据定位与证据层级。

## 选型表

| 现场 | 触发信号 | 选用方法 | 产出 |
|---|---|---|---|
| 断言的证据不够强 | 只观察到提示或响应码，没有回读或查询 | 证据分级 | 每条断言标注实际达到的证据层级 |
| 用例 FAIL，原因不明 | 已观察到预期被违反，但不知道为什么 | 失败诊断与最小复现 | 症状分类、最小复现步骤、证据三角 |
| 缺陷要提单 | 已确认是产品偏差，不是环境或用例问题 | 缺陷报告与严重度、优先级 | 可直接处理的缺陷单 |
| 修复后要复测 | 用户告知缺陷已修复 | 变更影响与回归范围 | 受影响用例集与分档范围 |

现场是"结果不稳定"时，不另设方法：按 SKILL.md 第 4 节保留首次失败与至多一次诊断性复现的规则处理。

## 证据分级与断言强度

**何时用**：任何一次判定。目的是让"PASS"可信——PASS 建立在什么证据上，读的人必须看得见。

**怎么做**

1. 给每条断言定下它应当达到的证据层级。
2. 执行时记录实际达到的层级。
3. 实际层级低于应达层级时不判 PASS：要么判 BLOCKED 并说明缺什么观察通道，要么改用可达成的层级并在结论里写明降级。
4. 结论写成"PASS（A3 重新查询一致）"这种形式，让读者知道 PASS 建立在什么上。

| 层级 | 观察到什么 | 能证明 | 不能证明 |
|---|---|---|---|
| L1 交互层 | Toast、气泡、按钮禁用态、HTTP 响应码 | 操作被发起、请求被受理 | 业务成功、数据落库 |
| L2 读取层 | 页面重新渲染后的元素、接口响应体字段 | 服务端返回了预期内容 | 已持久化、下游一致 |
| L3 持久层 | 重新查询、库中查询、跨页面刷新后仍一致 | 数据已落库且可再次读出 | 下游已同步、异步任务已终态 |
| L4 端到端层 | 另一个系统或另一个角色的视角看到一致结果 | 跨系统结果一致 | 未被观察到的边界情况 |

**例**：草稿改名用例。

- A1"保存后页面显示新名"属于 L2：页面重新渲染后的元素。
- A2"重新打开同一 ID 的草稿仍是新名"属于 L3：重新查询后一致。
- 只做了 A1 时，结论写 PASS（L2）并注明持久化未验证；用例要求 A2 而环境做不到时，A2 判 BLOCKED，整条不能算 PASS。

**常见遗漏**：把 L1 当 L3，Toast 出现就判落库；HTTP 200 当业务成功；只有 A1 却按 L3 写结论；同一用例里各断言层级不同，结论按最高层统一表述。

**何时不用**：需要先弄清为什么失败时用失败诊断，不必先分证据层级。

**与闸门的接口**：达不到应达层级又缺少观察通道（没有查询入口、没有日志权限）属于闸门问题：需要什么通道。不要因为"页面已经绿了"就降级放行。

## 失败诊断与最小复现

**何时用**：已观察到明确预期被违反（FAIL），但还不知道为什么；或需要给出别人能复现的最小步骤。

**怎么做**

1. **先定性症状**，不要急着找原因：阻断（操作无响应、白屏）、数据（流程走完但值不符）、时序（偶发、与顺序相关）、权限（拒绝或越权）、资源（超时、连接失败）。不同症状走不同的排查路径。
2. **先固定复现**：确认相同条件下能复现。复现不了就先归为结果不稳定，按 SKILL.md 第 4 节处理，不写成稳定缺陷。
3. **最小化**：逐步删减到不能删——删步骤、减数据、换角色、换时机。每删一次重跑一次。
4. **对照**：找一个能成功的邻近场景，比较差异点，差异点即嫌疑点。
5. **证据三角**：至少两条独立通道指向同一结论——应用日志、服务端日志、数据查询、监控或链路。只用一条通道时，结论要标注置信度。
6. **读代码定位**：有源码可读时可以定位到具体分支，但它给出的是对实现的推断，不是对现象的观察。写进缺陷记录时必须标为推断，断言仍只写观察到的行为；"代码看起来没改"不能计入 PASS 或回归范围的排除依据。
7. **收敛**：能定位到原因就写事实；不能定位就写已排除什么、嫌疑什么，不写猜测的根因。

**例**：草稿改名保存后重开仍是旧名。

- 定性：数据类，流程走完但值不符。
- 复现：连续 3 次重跑"改名并保存、重新读回"，3/3 复现。
- 最小化：去掉"退出详情页"仍复现；换成新建草稿不复现；换成 member-2 自己的草稿不复现。嫌疑收敛到"修改已存在草稿名称"这条路径。
- 对照：新建草稿并直接保存，成功。
- 证据三角：应用日志显示保存请求返回 200；按草稿 ID 查询库得到 name 仍为旧值。两条通道一致指向"保存未生效"。
- 结论：可写"保存请求被受理但值未变更"，不写"数据库写入失败"——未经证实。

**常见遗漏**：直接跳到根因猜想；只复现一次就下结论；最小化时把能成功的场景也一起删掉；只有一条证据通道就写"根因是"；把修复建议写成根因；把代码推断当成已观测事实写进断言。

**何时不用**：现象明确且原因已在需求或代码中确认（如"按规则拒绝"）时不必诊断，直接记 FAIL。

**与闸门的接口**：诊断需要的手段可能超出既有授权——读服务端日志、连数据库、改配置、造脏数据、访问监控。这些逐一走闸门。请求授权时写明要看什么、用来区分哪两个假设、拿到后怎样恢复。

## 缺陷报告与严重度、优先级

**何时用**：已确认是产品偏差（不是环境、不是用例问题、不是预期未定），需要产出一条别人能处理的缺陷单。

**怎么做**

1. **定性**：先分清是产品偏差还是其它，见 [exceptions.md](exceptions.md)。只有产品偏差才提单。
2. **最小复现步骤**：从诊断结果直接抄，每步可独立执行，标注前置状态与实际数据。不写"先做 A 再做 B"这种含糊表述。
3. **实际与预期**：预期写业务后置状态，不写实现细节；实际写观察到的现象和证据定位，附证据层级。
4. **严重程度**：按影响面、可恢复性、数据敏感度定，与修复成本无关。
5. **优先级**：按业务时窗与修复成本定，与严重程度独立。
6. **复现率**：N 次尝试中 M 次复现，写清 N 和 M。稳定复现写"N 次全部复现"。不要把"没再复现"写成"已修复"。
7. **关联**：标注关联用例 ID 与本轮运行记录，不覆盖修复前的证据。

| 严重程度 | 判据 |
|---|---|
| 阻断 | 核心流程无法完成，且无绕行方案 |
| 严重 | 核心流程能完成但结果错误、越权，或数据损坏且不可恢复 |
| 一般 | 非核心流程错误、局部数据不一致、存在绕行方案 |
| 建议 | 体验或表述问题，不影响结果 |

优先级与严重程度独立：看业务时窗（是否阻塞发布、是否影响当期承诺）与修复成本。严重但可延后的可以低优，阻塞性但易修的应高优。两者不一致时在单里写明理由。

**例**：成员归档他人草稿被拒绝，但拒绝后该草稿的归档标记被写入。

- 定性：产品偏差。预期"拒绝且不生效"，实际"拒绝但状态已变"。
- 最小复现：1）用 member-2 会话打开归属 member-1 的已提交草稿；2）执行归档；3）刷新列表并按草稿 ID 查询状态。3 步，3/3 复现。
- 预期：归档被拒，草稿状态仍为已提交。实际：界面提示无权，刷新后状态为已归档。
- 证据：列表页截图 + 按 ID 的状态查询返回 archived（L3）。
- 严重程度：严重——越权写入，且成员可把他人草稿归档。
- 优先级：高——影响权限边界，本迭代需修。
- 复现率：3/3。

**常见遗漏**：把修复建议写进根因；预期写实现细节（"应调用 checkPermission 返回 false"）而不是业务后置状态；严重程度按修复难度定；复现率只写"可复现"；把环境问题和产品缺陷混进同一张单。

**何时不用**：环境阻塞、预期未定、越权探测未获授权时都不提单，按闸门与例外表处理。

## 变更影响与回归范围

**何时用**：缺陷修复后要做复测；或需求、配置、依赖变更后要决定跑哪些。

**怎么做**

1. **列出变更**：代码、配置、依赖、数据、接口契约、基础设施里改了哪些。拿不到变更清单时先问，不要按印象推。
2. **推影响面**：从变更点向外推——被调用方、共享的数据与状态、共享的入口与配置、契约的下游。
3. **映射到用例**：影响面里的每个对象和操作对应到已有用例 ID。映射不到，说明可能有未设计的用例。
4. **分档**：冒烟（最快判定系统是否还活着）、重点（直接影响面）、全量（必要时）。
5. **给依据**：每条纳入或排除的用例都写"因为哪个变更、哪条影响"。没有依据的排除不能写。
6. **标明范围限制**：环境不具备、构造不出前置状态、基线已切换的，单独列出并说明它们未被验证。

**例**：修复"归档他人草稿被拒绝但仍写入归档标记"。

- 变更：归档接口的权限校验分支，一个函数。
- 影响面：归档入口的所有调用路径，即归档操作 × 角色（本人、他人）× 状态（草稿、已提交、已归档）。
- 映射：TC-ARCH-001 至 006，角色矩阵中"归档他人草稿"一行。
- 范围：重点档跑 TC-ARCH-002、003（他人归档被拒）与 TC-ARCH-005、006（终态再操作）；冒烟档顺带跑 TC-ARCH-001、004。
- 不跑：导出全部用例、名称长度用例。
- 依据：归档接口未出现在导出路径与名称校验路径上。
- 限制：TC-ARCH-006 需要"已归档草稿"作为前置数据，当前环境靠人工造数，标记为未验证。

**常见遗漏**：把"直接相关"当成只有失败的那一条；只跑修复点附近，不跑同一入口的其它路径；排除的用例不写依据；修复同时改了公共组件，却按"只改了一个函数"估算影响面；把旧基线的 PASS 当作新基线的通过。

**何时不用**：没有变更信息时不要凭猜测划范围，先问。

**与闸门的接口**：拿不到变更清单、无法确认新构建的基线、构造不出某个前置状态，都属于闸门问题。
