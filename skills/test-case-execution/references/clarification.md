# 澄清闸门：执行侧判定与恢复

在不确定某个条件是否阻断执行、该怎么问、以及答复后如何恢复时使用。

## 判定的核心问题

遇到执行困难时，只问三个问题：

1. **结论会因此改变吗？** 如果补上这个条件，可能导致 PASS、FAIL、BLOCKED 三种结论不同，它就是闸门。
2. **我能自己解决吗？** 授权范围内可安全准备的数据、自己能启动的服务，缺这些不算闸门。
3. **是环境问题还是产品问题？** 已证实的预期违背是缺陷，不是闸门，不要拿它去问用户；缺条件才是闸门。

## 触发与不触发

| 现场 | 判定 | 动作 |
|---|---|---|
| 需要管理员会话，环境里只有普通成员 | 闸门（身份不明） | 停，提出具体问题：要已登录管理员会话，还是允许创建测试角色 |
| 用例要验证"保存后重新打开仍是新值"，重开显示旧值 | 缺陷（FAIL） | 记录 FAIL 与证据，不提问掩盖 |
| 用例要读审计日志，但环境不提供该通道 | 闸门（观察通道不足） | 停，问审计记录的查看入口或接口 |
| 前置数据未创建，但可用项目已有方式创建测试草稿 | 不触发 | 自行创建，记录对象 ID 与清理方式 |
| 用例说 20 字上限，原型说 30，未指定版本 | 闸门（预期未定） | 停，回退到需求确认，不按现场行为判 PASS/FAIL |
| 目标环境 URL 未提供，但本轮范围里只有这一个环境且用户已说明 | 不触发 | 使用并记录实际地址 |
| 导出已受理，终态不可读，无 SLA | 闸门（判定口径未定） | 停，问状态观察途径或可接受时限；不自行判"性能失败" |
| 提交超时，服务可能已写入 | 不触发（但要谨慎） | 先按业务关联 ID 查询确认，再决定是否重发；仍不确定则停并提问 |

## 提问的写法

每个问题写五段：受影响用例 → 现象与证据 → 已排查了什么 → 需要什么条件 → 答复后怎样恢复。

反例：

- "环境有问题，测试跑不了。"——没有可回答的内容。
- "你要不要帮我登录一下？"——没说清需要哪个角色、哪个环境、恢复后做什么。

正例：

> Q-003：TC-EXP-002 需要以管理员身份导出全量数据，当前只有 owner-test（普通成员）会话，调用返回权限拒绝。
>
> - 受影响用例：TC-EXP-002、TC-EXP-005
> - 现象：HTTP 403，响应体 `permission denied`
> - 已排查：确认当前会话角色为普通成员；确认不是路径写错（同路径只读接口可访问）
> - 需要：具备导出权限的会话，或允许在测试环境创建具备该角色的账号
> - 恢复：拿到条件后重建导出任务并从步骤 1 重跑；其余用例不重跑

## 等待与授权

等待期间允许做的事：保存已完成用例的结果、证据和检查点；清理本次已创建且允许清理的数据。

等待期间不允许做的事：执行新用例；重发不确定结果的写操作；替换环境、身份或验收标准；把"环境可能有问题"当结论。

用户明确授权"可以创建测试角色""允许用 staging 代替"时，这属于授权不是含糊，可以继续，但须在执行记录中写明授权原话和实际使用的环境、角色标识。

## 恢复前检查

拿到答复后，逐项确认再继续：

| 检查项 | 不通过时 |
|---|---|
| 目标环境与答复中的环境一致 | 不一致则另开运行记录，不混入本次汇总 |
| 构建/版本标识仍是本次的基线 | 已切换则旧 PASS 不计入新基线，重跑受影响用例 |
| 会话角色符合答复 | 重新获取会话并复核 |
| 前序对象状态仍有效 | 重建对象，从用例初始状态重跑 |
| 时间窗口未过期 | 过期则重新建立数据 |

只对受影响用例恢复，不无理由重复全部已通过测试。

## BLOCKED 与闸门的关系

`BLOCKED` 是证据状态，闸门是工作状态，两者绑定：

- 标 `BLOCKED` 时必须已提出澄清问题（`Q-xxx`），只贴标签不算完成；
- 闸门关闭并补做后，该用例产生新的 PASS/FAIL 结论，与原 BLOCKED 记录关联而不是覆盖；
- 若答复始终无法到达，用例保持 BLOCKED，报告明确列出需要的条件和用户。

完整异常判定见 [exceptions.md](exceptions.md)。
