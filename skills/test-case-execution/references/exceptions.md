# 异常决策与恢复

遇到无法继续或不能确定结论时，先定位是测试条件、产品偏差、规则缺失还是观察能力不足。一次用例可同时包含已证实失败和未验证部分；不要为得到单一归因而删去事实。已确认是产品偏差但原因不明时，诊断步骤见 [execution-techniques.md](execution-techniques.md) 的失败诊断与最小复现。

| 现场事实 | 应如何判断与推进 |
|---|---|
| 管理员功能用例拿到的是普通成员会话，返回拒绝 | 前置角色不成立，BLOCKED；提出具体问题（要已登录管理员会话，还是允许创建测试角色），**停止本轮**，其余用例等待答复，不并行推进 |
| 用例要求验证普通成员被拒绝，实际返回规定的拒绝结果 | 按负向用例断言判断，不把预期拒绝记成 BLOCKED |
| 保存时显示成功，重开同一对象发现值未持久化 | 若持久化是明确断言则 FAIL；保存提示的 PASS 不能覆盖它 |
| 导出已受理，工具等待结束但任务终态不可读，未约定 SLA | 已观察部分记录通过，其余未验证；无其他明确违背时 BLOCKED，询问状态观察途径/时限后停止本轮，不能自行判“性能失败” |
| 故障注入用例要求断网后保留草稿，实际草稿丢失 | 前提与故障操作有效则 FAIL，不能因断网归为环境问题 |
| 上传请求超时，服务可能已写入数据 | 先按业务关联 ID 查询是否完成；不能确认时暂停重发并提问，记录可能残留 |
| 依赖服务完全不可用，无法建立前置状态 | BLOCKED，关联共同问题；若本用例就在验证依赖不可用时的降级，则继续按降级规则判断 |
| selector 失效，但页面中有明确同义按钮和同一业务路径 | 重新读取现场并定位，记录差异后继续；不能偷偷改走跳过被测 UI 的接口 |
| 用例说“名称最多 20 字”，原型说 30，未指定适用来源 | 预期未定属闸门：停止本轮并请求确认版本/规则；可记录现场行为，但相关断言不判 PASS/FAIL |
| 工具无实际测试结果、只输出“测试已生成”或零条执行 | 未发生的业务测试不能 PASS；执行能力缺失则 BLOCKED，尚未尝试则 NOT_RUN |

## 恢复前检查

以管理员会话缺失为例，保存已完成用例的结果与证据作为检查点，提出“需要已登录的测试管理员会话，还是允许创建测试角色”的具体问题，然后**停止本轮**；其余用例等待答复，不在同一轮内继续执行。用户补充会话后核对角色和目标环境，重新检查对象状态；只对受影响用例恢复，不无理由重复全部已通过测试。

等待期间若令牌过期、对象已处理、时间窗口结束或应用重新部署，原检查点可能失效。能够证明前序状态和证据仍有效时才继续剩余步骤；否则重建数据，从用例初始状态重新执行。前序失败的用例若是本条的必要依赖，本条记录 BLOCKED 与依赖关系，不能假装前置成功。

## 缺陷、阻塞与澄清的区别

- 有充分前置条件和明确预期，又观察到违背，就可记录缺陷；不要求先找到代码根因。
- 测试账号没有授权、数据不满足前提、预期未定，是条件/规则问题，不自动算产品缺陷。
- 若环境故障本身违反了本次明确验收要求，保留该失败；其导致的后续不可执行用例可另记阻塞。
- 不确定是否同一根因的多个失败，可按同类现象关联证据，不能凭猜测全部合并为一个已定位根因。

问题应附“答复后怎样恢复”，例如“提供具备 X 角色的会话后，重建草稿并从步骤 1 重跑”。清理或回滚不可行时列出残留和影响，请用户决定下一步，不扩大删除范围。

标为 BLOCKED 的同时必须已经实际提出澄清请求并停止；只贴标签不提问不算完成本轮。BLOCKED 描述证据状态，不代表条件已解决。
