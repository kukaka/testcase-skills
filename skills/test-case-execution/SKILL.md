# 测试用例执行

以负责测试结论的测试工程师身份工作：先验证能否正确执行，再操作、观察、比较和记录。成功调用工具、页面未报错或脚本退出码为 0，都不能单独证明用例通过。

**工作前提**：本 skill 采用澄清闸门。只要出现会影响执行或判定的未明确项，就停止当前执行并向用户提问，拿到明确答复后才继续。自行猜测环境、身份、判定口径或用"环境可能有问题"搪塞，都不能代替答复。

## 1. 接收用例与执行范围

读取用例、需求版本、项目运行说明和已有报告，确认目标环境与本次用例集合。支持任意已有用例格式，不依赖安装编写 skill；需要映射字段时读取 [references/run-record.md](references/run-record.md)。保留原用例 ID、步骤与断言，不在执行过程中悄悄降低标准。

记录实际可得的构建/版本标识；拿不到构建号时写明所用地址、执行时间和版本未知的限制，不虚构版本，也不自动阻塞与版本无关的测试。环境用途或目标身份不明且会影响测试操作时必须询问。遇到失败诊断、证据强度、缺陷提单或修复后回归范围的问题时，读 [references/execution-techniques.md](references/execution-techniques.md)。

## 2. 澄清闸门：不明确就停

出现下列任一情况，**立即停止当前执行**，不要并行推进其他用例：

| 触发停机 | 判断依据 |
|---|---|
| 目标不明 | 测哪个环境、哪个版本或构建不确定，且会影响结论 |
| 身份/授权不明 | 需要的角色或会话是否存在、是否允许获取或创建未知 |
| 数据来源不明 | 前置对象从哪来、能否在授权环境内安全创建不确定 |
| 观察通道不足 | 用例要求的断言没有可用观察手段（页面、接口、日志、查询） |
| 预期未定 | 用例预期缺失、规则来源冲突，或设计仍处于待澄清状态 |
| 操作越界或结果不确定 | 操作影响超出现有授权，或提交结果不确定且重做可能重复生效 |

下列情况**不触发停机**，自行处理并记录：

- 说明里已有可靠答案；
- 能在授权测试环境内安全准备数据、且准备方式明确——自行准备，记录实际值与对象标识，不重复请用户确认；
- 找到不改变业务含义的等价入口——记录路径差异后继续；
- 对象 ID、临时路径等无业务含义的细节。

停机时的动作：

1. 收集全部已识别的闸门问题，为每个分配 `Q-xxx`，写清受影响用例、现象/证据、已排查内容、需要什么条件、答复后怎样恢复。
2. 用宿主可用的提问工具或对话把问题实际问出来；集中提出，不擅自联系外部负责人。宿主没有可交互提问能力时，把问题写在回复里，同样停在这里。
3. 停止。保存已完成用例的结果与证据作为检查点，但不再执行新用例，不自行替换目标环境、身份或验收标准。排序不改变闸门语义：为绕开阻塞而把阻塞用例排到最后，不构成继续执行的理由；一旦命中闸门即停止本轮。

等待期间：

- 沉默、超时不是答复。不轮询、不重复提交写操作、不擅自扩大授权范围。
- 若用户明确授权由你创建角色、准备数据或使用替代环境，这不属于含糊，可以继续，但须记录授权来源和实际使用的环境与身份。
- 部分答复只解决一项时，剩余项**继续停机**。

答复到达后：

1. 规则类答复必须先落回用例预期，再执行；把答复来源写入执行记录。
2. 重新核对目标环境、构建、角色、对象状态和时间有效性；确认仍有效才从检查点继续，否则重建状态重跑受影响用例。
3. 修复后复测使用新尝试记录，并检查直接受影响的回归范围；旧基线的 PASS 不计入新基线汇总。

细则、提问范例和恢复流程见 [references/clarification.md](references/clarification.md)。方法执行需要的额外授权——读服务端日志、连数据库、改配置、造数据、访问监控——同样走本节闸门，不为了定位问题自行扩权。

## 3. 执行：前置状态 → 动作 → 观察 → 判定

先创建一次独立运行记录，默认 `tests/runs/<run-id>/report.md`，证据放在该运行目录下；遵循用户已有位置。按风险和显式依赖排序，必要时先做最小连通性检查。连通性检查不能代替业务用例；若共同前提失败，记录共享阻塞，不对每个用例重复制造相同失败。

逐条执行：

1. 核对本用例的角色、数据和初始状态。多角色使用隔离会话，关联同一个业务对象。前置状态无法建立时先区分环境准备不足和明确的产品偏差。
2. 从实际 UI/工具返回确定操作对象；不使用猜测的 selector 或过期页面引用。保留步骤序号、实际数据标识和关键动作结果。
3. 动作后等待可观察条件，比较**所有纳入用例的断言**。异步任务区分请求受理、处理完成和业务结果；需要时刷新/重新查询验证持久性。工具超时不等于违反业务 SLA，没约定时长就询问或记录无法判断。
4. 给每个断言记录观察、结果和证据定位；截图适合 UI，响应/日志/查询适合数据与接口，不强制每一步截图。证据只证明其覆盖的事实，Toast 不证明落库，HTTP 200 不证明业务成功。证据层级（交互、读取、持久化、端到端）的分级与结论写法见 [references/execution-techniques.md](references/execution-techniques.md)。
5. 每个用例完成或阻塞后及时保存结果、数据残留及下一步。保护认证状态和敏感数据，不把凭据写入产物。

已知产品偏差即使原因不明仍应如实记录；不要为了给出根因而推测。测试只授权执行与记录时，不自行修复产品、变更断言、对外提单或发布消息。发现范围外的问题，记录观察与影响，避免无边界扩大测试。

## 4. 判定结果，保留首次事实

| 状态 | 判定规则 |
|---|---|
| `PASS` | 前置条件有效，且本用例全部断言均已实际验证符合预期 |
| `FAIL` | 有有效证据证明至少一个明确预期被违反；即使其余断言受阻，也保留失败并列出未验证项 |
| `BLOCKED` | 尚无已证实的预期违背，但缺少条件或证据无法完成判断，含部分执行后受阻 |
| `NOT_RUN` | 本次选定但尚未尝试、且未确定阻塞原因，例如时间不足或用户中止 |

故意撤销权限、模拟断网等本来就是用例动作时，按其预期判断；预期中的拒绝不是环境阻塞。完整决策和恢复案例见 [references/exceptions.md](references/exceptions.md)。不能把未运行、跳过、零测试结果或仅生成了脚本算成 PASS；独立明确的断言已经失败时也不能用"环境可能有问题"覆盖事实。

标为 `BLOCKED` 的同时必须已经实际提出澄清请求并停止；只贴一个 BLOCKED 标签而没有提问，不算完成本轮。`BLOCKED` 描述的是证据状态，不代表问题已被解决。

已确认 `FAIL` 而原因不明时，按 [references/execution-techniques.md](references/execution-techniques.md) 的失败诊断与最小复现处理：先定性症状，再最小化，再用两条独立通道交叉验证。定位不到就写已排除什么、嫌疑什么，不写猜测的根因，也不把修复建议写成根因。

复现前先判断重复操作是否安全以及是否能重建状态。没有现成重试策略时，对可安全重做的问题至多追加一次诊断性复现；仍不明就报告并澄清，不循环尝试到成功。每次尝试单独记录，首次失败后成功标注"重试通过/结果不稳定"，保留首次 FAIL，不默认为通过。不可重复或结果不确定的写操作先查询再决定，无法核对就停止重发。

## 5. 恢复、复测与报告

收到条件或规则答复后，更新问题记录和受影响用例的执行副本，保留原始版本与答复来源。恢复前重查版本、会话、数据、时间有效性和前序状态；只有这些均仍有效才可从检查点继续，否则从可复现的初始状态重新执行。若执行中切换构建或需求基线，应分开运行记录或逐用例标明基线；旧 PASS 不纳入新基线的通过汇总，按变化确认复测范围。修复后复测使用新尝试/运行记录，并按 [references/execution-techniques.md](references/execution-techniques.md) 的变更影响与回归范围划定受影响用例集，每条纳入或排除都写依据；不覆盖修复前证据。

按 [references/run-record.md](references/run-record.md) 汇总所选用例及断言、问题、缺陷与残留。缺陷单按 [references/execution-techniques.md](references/execution-techniques.md) 区分严重程度与优先级：严重程度看影响面、可恢复性与数据敏感度，优先级看业务时窗与修复成本，两者可以不同。清理仅限本次创建且允许清理的数据，清理失败单列，不抹去业务断言结果。用户中止时保存进度，不继续业务操作。

报告各状态数量及范围差异，说明重试、人工代验、环境限制和未解决问题。若给通过率，明确分母；它不能掩盖 BLOCKED/NOT_RUN 或替代发布决策。最终回复给出报告位置、主要结论、待回答问题和恢复条件，而不是笼统的"全部完成"。存在未关闭的 `Q-xxx` 时，必须在回复中明确列出这些问题和恢复条件。
